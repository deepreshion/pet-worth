# ADR-001: технический стек MVP

Статус: **Утверждено**  
Дата решения: **23 сентября 2026 года**

## 1. Контекст

Pet Worth — мобильное приложение для iOS и Android с профилями питомцев, медицинской хронологией, документами, семейным доступом и напоминаниями.

Для MVP важны:

- быстрый выпуск небольшой командой;
- использование опыта команды с Vue;
- одна клиентская кодовая база для iOS и Android;
- безопасная реляционная модель семей, ролей и питомцев;
- загрузка фотографий и PDF в закрытое хранилище;
- push-уведомления и deep links;
- возможность позже заменить отдельные облачные компоненты без полной переработки клиента.

## 2. Решение

Для MVP выбран стек **Ionic Vue + Capacitor + Supabase**.

### Клиент

- Vue 3;
- TypeScript;
- Ionic Vue;
- Capacitor;
- Vite;
- Vue Router;
- Pinia;
- TanStack Query for Vue;
- vee-validate и Zod;
- CSS variables и собственные компоненты дизайн-системы.

Ionic-компоненты используются для навигации, модальных окон и ожидаемого мобильного поведения. Фирменные карточки и визуальные элементы Pet Worth реализуются собственными Vue-компонентами.

### Облачная часть

- Supabase Auth;
- PostgreSQL;
- Row Level Security для каждой доступной клиенту таблицы;
- Supabase Storage с приватными buckets;
- PostgreSQL functions и Supabase Edge Functions для привилегированных и атомарных операций;
- Supabase Cron для поиска наступивших напоминаний;
- APNs и FCM для доставки push-уведомлений.

### Качество и эксплуатация

- Vitest и Vue Test Utils для unit- и component-тестов;
- Maestro для основных сценариев на реальных мобильных сборках;
- тесты RLS и database functions в локальном окружении Supabase;
- Sentry для ошибок без передачи медицинского содержимого;
- GitHub Actions для проверок и автоматизации сборок;
- нативные сборки через Xcode и Gradle.

## 3. Архитектурные правила

1. Бизнес-правила не размещаются только в Vue-компонентах.
2. Проверка семейного доступа выполняется в базе через RLS.
3. Опасные и составные изменения выполняются через database functions или Edge Functions в одной транзакции.
4. В мобильном приложении используется только публичный ключ Supabase; `service_role` разрешён только в доверенной серверной среде.
5. Документы хранятся в приватных buckets. Постоянные публичные ссылки запрещены.
6. Push содержит минимум информации и не раскрывает медицинские данные на заблокированном экране.
7. Состояние напоминания хранится в PostgreSQL; факт доставки push не означает выполнение напоминания.
8. Полноценное offline-редактирование и разрешение конфликтов не входят в MVP. Допускается локальный кэш для чтения ранее загруженных данных.
9. Клиент обращается к Supabase через отдельный слой сервисов и composables, а не напрямую из экранных компонентов.

## 4. Последствия решения

### Положительные

- команда использует знакомую экосистему Vue и TypeScript;
- большая часть интерфейса разрабатывается и проверяется в браузере;
- одна кодовая база покрывает iOS, Android и при необходимости PWA;
- PostgreSQL соответствует реляционной модели семейного доступа;
- для MVP не требуется эксплуатация собственного API-сервера и очереди задач.

### Ограничения

- интерфейс работает внутри WebView, поэтому сложные анимации и очень большие списки потребуют дополнительной оптимизации;
- часть мобильных функций зависит от Capacitor-плагинов и может потребовать кода на Swift или Kotlin;
- нативные проекты iOS и Android остаются частью репозитория и требуют проверки после обновлений Capacitor;
- фоновые возможности iOS и Android различаются, поэтому приложение не должно полагаться на фоновое выполнение клиентского JavaScript;
- Supabase уменьшает объём инфраструктурной работы, но создаёт зависимость от платформы.

## 5. Рассмотренные альтернативы

### Flutter

Даёт более предсказуемый мобильный рендеринг, сильную основу для сложного offline-first приложения и богатых анимаций. Не выбран для MVP из-за перехода команды на Dart и отсутствия требований, оправдывающих эту стоимость сейчас.

### React Native с Expo

Подходит для кроссплатформенного приложения и имеет удобную инфраструктуру сборок и push. Не выбран, поскольку React не является основной технологией команды.

### Собственный backend

NestJS с PostgreSQL, объектным хранилищем и отдельным worker даст больше контроля. Отложен, поскольку увеличивает срок MVP и эксплуатационную нагрузку до проверки продуктовой гипотезы.

## 6. Условия пересмотра

Решение пересматривается, если выполняется хотя бы одно условие:

- прототип на реальных устройствах не обеспечивает требуемую плавность интерфейса;
- приложение становится полноценно offline-first с двусторонней синхронизацией и сложным разрешением конфликтов;
- появляются тяжёлые фоновые вычисления или глубокая интеграция с системными API;
- стоимость или ограничения Supabase становятся существенными;
- юридические требования требуют отдельного контролируемого контура хранения и обработки данных;
- команда меняется и основная экспертиза переходит к другой мобильной платформе.

Пересмотр оформляется новым ADR; этот документ после утверждения не переписывается задним числом.
